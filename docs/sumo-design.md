## 0. 方針

**Phase 1 で作った層[2](ネットワーク)は資産としてそのまま使い、層[3]だけを SUMO に替える。**

| 層 | 移行後 |
|---|---|
| [1] データ取得 | 変更なし |
| [2] ネットワーク | 変更なし。`edges.gpkg` / `network_conflated.gpkg` / `signal_plans.json` / `census_hourly.json` を SUMO 入力へ**変換する層**(`sumo/`)を追加 |
| [3] シミュレーション | **SUMO に置き換え**。自前の IDM / MOBIL / サブレーン / 交差点は撤去 |
| [4] キャリブレーション | SUMO を繰り返し起動する形に変更(§7) |
| [5] 可視化 | SUMO の FCD 出力を既存ビューワ形式へ変換(§8) |

**なぜ置き換えるか:**

- IDM・サブレーン車線変更(SL2015)・対向車へのギャップ受容・信号制御・
  滞留長計測が実装・検証済みで揃っている。自前実装で残っていた簡略化
  (交差点内の交錯待ちが交差方向を塞がない、車種が乗用車のみ)も解消できる
- 需要生成(`jtrrouter` = 流入 + 転回率、`routeSampler` = 断面交通量からの経路生成)が
  本プロジェクトの需要方式(design.md §3.2)とそのまま対応する
- 自前実装の検証工数(design.md §8.2 の欠点)を Phase 3 以降のキャリブレーションに回せる

### 0.1 既存資産のフル活用

**現況再現性を上げるため、手元にある既存データ・知見はすべて SUMO 入力へ流し込む。**
自前実装では表現力の制約で捨てていた情報も、SUMO なら表現できるものが多い。
下表の「自前実装」列が空欄のものは、今回初めて使う情報。

| 冬季パラメータ・`sublane_loss` | 使用 | 冬季 vType・冬季ネットワーク | §5.4 |
| 転回率生成(飢餓修正済み)・行き止まりの流出扱い・巡回上限 | 使用 | 純関数に移植して `turns.xml` を生成 | §4.2 §4.3 |
| 断面照合の枠組み(`scripts/40`)とベースライン | 使用 | 形式を変えずに SUMO 出力で回す。自前実装の値と並べる | §6 |
| 自前実装のテスト群(飽和交通流率・右折の譲り・左側通行・スピルバック) | 使用 | **同じシナリオを SUMO の受け入れテストとして移植** | §10 |
| ビューワと再生データ形式 | 使用 | FCD を同じ形式に変換 | §8 |

**守る原則(architecture.md から引き継ぐ):**

- 層[2]の出力は不変。SUMO 入力はそこから**機械的に再生成できる**(手で net.xml を編集しない)。
  手入力が要る情報は層[2]の手入力データ(issue #1)に入れ、変換で反映する
- ID で KSJ まで遡れる(SUMO edge id → `eid` → `ksj_ids`)
- 各スクリプトは `reports/NN_*.json` を出す
- 閾値・パラメータは定数として1箇所に置く

## 2. ネットワーク変換(`sumo/netgen.py`)

netconvert に **plain XML**(nod/edg/con)を渡す。Shapefile 入力や OSM 入力は使わない
(一方通行・車線・速度・一時停止など、層[2]で解決済みの情報が落ちるため)。

### 2.1 ID と座標

| SUMO | 由来 |
|---|---|
| node id | `nid`(`network_conflated.gpkg` nodes) |
| edge id | `eid`(`edges.gpkg`)をそのまま文字列化 |
| 座標 | EPSG:6679 の値をそのまま渡す |

- `--offset.disable-normalization true` で**座標を正規化させない**。
  SUMO 座標 = EPSG:6679 となり、FCD 出力をビューワへ渡すときの変換が
  既存(`scripts/33` の `x - cx`)と同じになる
- 対向ペアは `linked_edge` を param として残す(断面交通量の集計で使う)。
  `census_id` / `ksj_ids` も edge の `<param>` に入れる

### 2.2 左側通行

**`--lefthand true` を必須にする。** 自前実装の MOBIL `a_bias` の符号と同じ理由で、
誤ると右折が対向直進と交錯しない・追越が逆になる。テストで固定する(§10)。

SUMO の左側通行では lane 0 = 路肩側(左端)、最大 index = 中央側(右端)。
右折は中央側の車線から出る。

### 2.3 立体交差(創成トンネル等)

- 位相は層[2]で解決済み(立体リンクは端点以外で地表と共有ノードを持たない)。
  netconvert には**明示的な node id で接続を与える**ので、座標が近いだけの
  ノードは結合されない
- **`--junctions.join` は使わない。** 近接ノードを1つに縮約するため、
  坑口付近で地表とトンネルを誤接続する。短リンク統合は層[2]で済んでいる
- **`--geometry.remove` も使わない。** 次数2ノードを消して edge を連結し、
  edge id が `eid` と1対1でなくなる(センサス照合と KSJ 遡及が壊れる)

### 2.4 車線とサブレーン

| edge 属性 | 由来 |
|---|---|
| `numLanes` | `n_lanes` |
| `width`(車線幅) | `carriageway_m / n_lanes` |
| `speed` | `speed_kmh / 3.6` |
| `priority` | 道路分類(`category`)と車線数から。一時停止の流入は最低(§2.6) |

サブレーンは SUMO のサブレーンモデル(`--lateral-resolution`)で扱う。
解像度は層[2]と同じ **1.75 m**(`network.lanes.SUBLANE_W_M`)。
乗用車(幅 1.8 m)は約2サブレーンを占め、自前実装と同じ粒度になる。

> 自前実装の `n_sublanes` は SUMO には直接渡さない。
> SUMO は車線幅と `lateral-resolution` から帯を決める。

### 2.5 右折専用車線

`right_turn_lane = 1` の edge は、停止線手前 60 m(`RT_ZONE_M`)で
**中央側に1車線を足す**(edg.xml の `<split pos="-60" lanes="..."/>`)。

- 足した車線は右折専用、既存車線は直進・左折用にする
  (con.xml で車線ごとの接続を明示する)
- 実効幅が足りない edge(自前実装の `RT_MIN_SUB` 相当 = 直進1車線を残せない)には
  足さない。専用車線なしの edge では右折待ちが後続を止める(実態どおり)

### 2.6 無信号交差点と一時停止

| ケース | node type |
|---|---|
| 信号あり(173 ノード) | `traffic_light`(§3) |
| 一時停止の流入を含む(119 箇所) | `priority_stop`。一時停止の流入 edge の priority を下げ、従道路側にする |
| その他 | `priority`(道路分類・車線数で優先道路を決める) |

一時停止は**流入方向単位**の情報(architecture.md §4.2)。`io.load_network_inputs` の
`stop_edges` をそのまま使い、該当 edge だけを従道路にする。

### 2.7 転回

- **U ターンは作らない**(`--no-turnarounds true`)。自前実装の「対向 Edge へは転回しない」と同じ
- 指定方向外進行禁止(転回制約)は北海道の JARTIC に無く、手入力(issue #1)。
  入力が揃った時点で con.xml に `<delete>` として反映する。それまでは netconvert の
  接続推定に任せる
- 行き止まり(創成トンネル坑口などネットワーク外へ続く端)は SUMO でも流出端になる

### 2.8 netconvert のオプション

```
netconvert -n sapporo.nod.xml -e sapporo.edg.xml -x sapporo.con.xml -i sapporo.tll.xml
  --lefthand true
  --offset.disable-normalization true
  --no-turnarounds true
  --junctions.join false          # 既定値だが明示する
  --geometry.remove false         # 同上
  --tls.guess false               # 信号は tll.xml で与える
  -o sapporo.net.xml
```

### 2.9 車線規制(専用通行帯・通行止め・進行方向別通行区分)

JARTIC 規制情報の線規制のうち、自前実装では使っていなかったもの。層[2]の
conflation(線規制と同じバッファ + 方位角条件)で edge に結合し、`edges.gpkg` に列を足す。
**SUMO 入力の変換だけで処理せず、層[2]に入れる**(ビューワ・レポートからも見えるように)。

| 規制 | 区域内 | 時間帯 | SUMO での表現 |
|---|---|---|---|
| 専用通行帯(バス) | 10 本 | 7:30〜9:00 / 9:30 | 路肩側の車線(lane 0)を `allow="bus"` にしたネットワーク変種を作り、時間帯で切り替える(§2.11) |
| 路線バス等優先通行帯 | 1 本 | 7:30〜9:00 | 一般車も通れるが、バスの接近で空ける義務。第一段では通常車線として扱い、影響を未解決事項に残す |
| 車両通行止め(終日) | 2 本 | 0〜24 時 | edge を全車種通行不可(`disallow="all"`)。位相は残して歩行者の横断用に使える状態にする |
| 車両通行止め(時間帯) | 3 本 | 13〜18 時 / 7〜22 時 | 対象時刻に閉鎖(§2.11) |
| 車両通行帯・進行方向別通行区分 | 16 本 | — | 車線数の検算に使う。方向別の車線割当は属性(`dir_*`)が空のため自動では入れられない。該当箇所を一覧にして手入力(issue #1)へ回す |
| 転回禁止 | 7 本 | — | U ターンは全面的に作らないので追加処理なし |

**時間帯の規制は照合時刻(8時・13時)に効く**。専用通行帯は朝8時の照合で一般車線が1本減る。
通行止め(13〜18時)は昼13時の照合に効く。

### 2.10 横断歩道と歩行者

design.md §1.3 は「歩行者の明示的モデル化はしない(地下歩行空間で地上横断が少ない)」としていた。
横断そのものは少なくても、**右左折車が横断歩道で歩行者に譲る**ことは交差点の捌け量を
下げる。区域内の横断歩道は 183 箇所ある(JARTIC 点規制)。

- netconvert に横断歩道を生成させる(JARTIC の横断歩道点を最寄りノードの流入/流出に結合し、
  con.xml の `<crossing>` として明示する)
- 歩行者需要は観測が無いので**キャリブレーション用のパラメータ**にする
  (横断歩道ごとの時間当たり歩行者数。既定は0 = 自前実装と同じ条件)
- 斜め横断可(6 箇所)はスクランブル交差点。§3.3 の歩行者専用現示と対応させる
- 第一段(Step 1〜2)は横断歩道を生成するだけにし、歩行者需要は既定0で比較する。
  歩行者を流すかは Step 2 のベースラインを見て決める

### 2.11 時間帯で変わる規制の扱い

専用通行帯・時間帯通行止めは、照合時刻ごとに**ネットワーク変種**を作って扱う
(`sapporo_h08.net.xml` など)。1回のシミュレーションは照合時刻の前後 40 分
(warmup 600 s + record 1800 s)なので、途中で規制が切り替わることは無い。
終日のシミュレーションが必要になった時点で、TraCI による車線許可の動的変更に切り替える。

**受け入れ条件:** netconvert の警告件数と、生成された edge 数 = 1,176(右折車線の
split で増えた分を除く)を `reports/50_sumo_net.json` に出す。
到達可能性(全流入 edge から流出 edge へ経路あり)を sumolib で再検査する。

## 3. 信号(`sumo/tls.py`)

### 3.1 現状のデータ

- 信号ノード 173、うち JARTIC の信号計画(時間帯別サイクル長・スプリット・
  現示ごとの流入リンク)と結合できたのは **20**
- JARTIC の現示定義は流入リンクを DRM リンク番号で持つが、**DRM リンクの座標は無い**
  (有料版)。どの現示がどの流入方向かを機械的に決められない

### 3.2 現示計画の作り方

自前実装(`NNode.green`)と同じ **2現示**(東西 / 南北、グリッド軸で判定)から始める。

```
[東西 青] → [東西 黄] → [全赤] → [南北 青] → [南北 黄] → [全赤]
```

- 青信号中の右折は **`g`(従属青)** にする。SUMO の交差点モデルが対向直進・左折に
  ギャップ受容で譲る。自前実装の「右折は対向にギャップ受容(5.5 s)」に対応
- 黄 3 s・全赤 2 s(JARTIC の `yellow_s` / `all_red_s`。無い交差点は同値を既定)。
  自前実装は黄と全赤を合わせた損失 3 s だったので、青時間は SUMO 版のほうが各現示 2 s 短い
- **作り方(実装)**: netconvert の1回目で接続と linkIndex を確定させ、sumolib で読んで
  2現示の計画を作り直し、`-s … -i tll.xml` の2回目で上書きする(`sumo/build.py`・`sumo/tls.py`)。
  軸の判定とオフセットはケースのフック(札幌: `cases/sapporo.py` の `signal_axis` /
  `signal_offsets` = 自前実装と同じ東西青始まり・東行き green wave 40 km/h)。
  フックが無いケースは優先度が最も高い流入の向きを A 軸、オフセット 0 にする
- SUMO の `offset` は「A 青の開始時刻」(自前実装の `(t - offset) % cycle` と同じ向き)。
  `test_signal_offset_is_start_of_a_green` で固定した
- 信号ノード 173 のうち 6 は流入だけ/流出だけの端点(制御する交差が無い)で、
  netconvert が信号を作らない。SUMO 上の信号は 167
- サイクル長: JARTIC 結合済みの 20 ノードは**照合時刻のサイクル長**(`by_hour`。
  自前実装は全時刻の中央値だった)、それ以外は 120 s(自前実装と同じ既定値)

### 3.3 JARTIC の現示・スプリットを使う

20 交差点は現示数 3〜6、スプリット、現示ごとの流入リンク番号を持つ。これを捨てずに使う。

- 現示の `in`(流入リンクの番号の集合)で現示をまとめる。例: `in: [1,2]` の2現示と
  `[3,4]` の2現示 → 「方向 A の青 + A の右折矢印」「方向 B の青 + B の右折矢印」
- 同じ `in` 集合の中で**スプリットの大きい方を主青(直進・左折・従属青の右折)、
  小さい方を右折矢印(右折のみ `G`)**とする
- `in` が全流入を含む短い現示は歩行者専用現示(スクランブル)または全赤とみなす
- 方向 A/B のどちらが東西か: DRM リンク座標が無いので、**スプリット合計の大きい方を
  センサスで交通量の多い軸(幹線側)に割り当てる**。20 交差点しかないので、
  全件を航空写真・現地知識で目視確認し、結果を層[2]の手入力データに固定する
- 変換した現示は `reports/50_sumo_net.json` に交差点ごとに出し、目視確認の記録にする

JARTIC 交差点座標 231 件のうち、制御情報(定義)を持たない交差点も番号は同定できる。
制御情報の追加取得ができた場合に同じ手順で取り込めるよう、番号 ↔ ノードの対応を残す。

### 3.4 オフセット

オフセットは Phase 3-③ のキャリブレーション対象。`tlLogic` の `offset` 属性で与える。
ネットワークは作り直さず、**オフセットだけを持つ追加ファイル**(`tls_offsets.add.xml`、
同じ `id`/`programID` の `tlLogic` を上書き)を試行ごとに生成する。

## 4. 需要(`sumo/demand.py`)

方針は design.md §3.2 のまま(**OD は使わない。コードン流入 + 転回率**)。
SUMO では **`jtrrouter`** がこの方式そのものなので、これを使う。

### 4.1 流入

- 流入 edge = 無向次数1ノードから出る edge(自前実装の `_degree1_nodes` と同じ規則。
  63 本)
- レート: センサス時間帯別交通量(方向平均)が結合できる 9 本はその値。`sim.demand.hourly_rate` を流用
- **区域外のセンサス 18 区間を使う**: 流入 edge の上流(区域外)にセンサス区間があれば、
  その時間帯別交通量を割り当てる。流入 edge の始点から区域外区間の線までの距離と
  方位角差で結合する(層[2]の線規制 conflation と同じ条件)
- 残りは既定値(幹線 500 / 細街路 150 台/時)。**既定値で埋めた流入の本数と台数を
  レポートに出し**、Phase 3-② で優先的に疑う対象にする
- Phase 3-① の申し送り(国道36号の境界流入点の欠落、創成トンネルの通過交通
  2,400〜2,800 台/時が再現不能)は、この結合を作る段階で流入 edge の一覧と突き合わせて確認する
- `flows_h{HH}.xml` に `<flow from="<eid>" begin end vehsPerHour departLane="best" departSpeed="max">`
  として書く。到着はポアソン(`period="exp(...)"`)

### 4.2 転回率

- `turns_h{HH}.xml`(`edgeRelations`)に **流入 edge → 流出 edge ごとの確率**を書く
- 初期値は自前実装と同じ: 転回クラス(直進/左折/右折 = 0.70/0.15/0.15)を存在する
  転回先で再正規化し、クラス内の複数候補(上下分離・並走車道)は角度適合の重み
  `1/(1+ずれ)²` で配る。**このロジックは netsim から純関数として移植**する
  (Phase 3-① で直した「最良1本だけだと半分の Edge が飢餓する」問題を再発させない)
- 流出 = 転回先の無い edge。`<sink>` として明示する

### 4.3 巡回の上限

自前実装は通過交差点数 30(`MAX_HOPS`)で最寄り出口へ向けていた。SUMO 版も同じ扱いにする:
`jtrrouter` の経路を**後処理で**、通過交差点(層[2]の Edge)が 30 を超えた時点から
最寄りの流出 Edge への最短経路につなぎ替える(`sumo/demand.py` の `cap_hops`)。

- `jtrrouter` の経路長の打ち切り(`--max-edges-factor`)は、打ち切った地点で車両が
  区域の途中で消えるため使わない(無限経路の安全上限としてだけ 0.5 を渡す)
- つなぎ替えた台数を `reports/40_demand_check_sumo.json` の `routes.n_hop_capped` に出す
- `jtrrouter` は存在しない流入 Edge の flow を黙って捨てるので、経路の台数が流入の合計と
  一致することを検査する

> 経路が出発時に決まるのは自前実装(交差点ごとに抽選)と違うが、
> 転回が各交差点で独立な確率なら統計的には同じ。

### 4.4 車種

センサスは小型(`s`)/大型(`l`)を時間帯別に分けて持つ(大型車混入率 2.8〜12.9%)。
自前実装は大型も乗用車1台として数えていたが、SUMO では**大型車 vType を混入させる**。

- 流入 edge ごとに、結合したセンサス区間の照合時刻の `l / (s + l)` を大型車比率にする。
  センサスの無い流入は区域内区間の加重平均
- 大型車: 車長 12 m、幅 2.5 m、`accel` / `decel` は乗用車より小さく、`tau` は大きく
  (値は SUMO の truck 既定を出発点に、定数として1箇所に置く)
- `vTypeDistribution` で乗用車と混ぜ、flow の `type` に指定する
- **自前実装との比較用に、大型車比率 0 で回すオプションも残す**(移行の差分と
  大型車の効果を切り分けるため)

## 5. 車両モデル(`sumo/vtypes.py`)

### 5.1 縦断: IDM

SUMO の `carFollowModel="IDM"` を使う。平常時の値は Phase 2-① で飽和交通流率
1,845 台/時/車線に合わせた値を引き継ぐ。

| architecture.md §5.2 | SUMO vType 属性 | 平常時 | 冬季 |
|---|---|---|---|
| `a` | `accel` | 1.5 | 0.7 |
| `b` | `decel` | 1.8 | 0.55 |
| `s0` | `minGap` | 2.0 | 5.0 |
| `T` | `tau` | 1.1 | 1.6 |
| `delta` | `delta` | 4 | 4 |
| `coeff_v` | `speedFactor` | `normc(0.95,0.08,0.7,1.3)` | 平均 × 0.7 |

- 車長 4.5 m、幅 1.8 m(自前実装の `CAR_LEN` と揃える)
- **SUMO の IDM で飽和交通流率を再測定し、1,800〜2,000 台/時/車線に入ることを確認する**
  (§10)。SUMO は交差点通過時の挙動が自前実装と違うため、同じパラメータで
  同じ値になる保証は無い。外れたら `tau` / `minGap` を合わせ直す

### 5.2 時間刻み

`--step-length 0.5`(自前実装と同じ。0.2 s に細分しても飽和交通流率が 1% も変わらないことは
Phase 2-① で確認済み)。SUMO の IDM は内部で `stepping` 分割するので、刻みによる振動は
自前実装より出にくい。

### 5.3 横断: サブレーン車線変更

`--lateral-resolution 1.75` を与えると SUMO は車線変更モデル SL2015 を使う。
左側通行では「空けば左に戻る(左寄せ)、追越は右から」が `--lefthand` の下で
SUMO 側の既定挙動になる。自前実装の MOBIL 独自パラメータ(`A_TH` / `A_BIAS`)は
SL2015 の `lcStrategic` / `lcKeepRight` / `lcSpeedGain` などに置き換わる。
対応は1対1ではないので、**挙動テスト(右から追い越す)で確認**する。

### 5.4 冬季

- 車両: §5.1 の冬季パラメータを持つ vType に差し替える
- 道路: 雪堤による幅員減少は、**冬季用ネットワーク**(`sapporo_winter.net.xml`)を
  車線幅 × (1 − `sublane_loss`) で生成して表す。自前実装の `sublane_loss = 0.25`
  (実効サブレーンを減らす)と同じ意味。サブレーンモデル下では車線幅が狭いほど
  すり抜け・並走ができなくなる
- 雪堤は路肩側(lane 0 側)だが、SUMO は車線内の横位置を幅に比例して扱うので、
  第一段では幅の一律縮小で近似する

## 7. キャリブレーション(層[4])への影響

### 7.1 実行形態の変更

architecture.md §1・§6.3 は「層[3]をプロセス内で繰り返し呼ぶ。ファイル経由にしない」と
定めていた。SUMO では次のように変える:

- 1試行 = SUMO を1回起動。試行ごとに変わるのは**追加ファイル
  (オフセット・vType・経路)だけ**で、net.xml は共有して再生成しない
- 起動は **libsumo**(プロセス内。TraCI のソケット通信より速い)を第一候補、
  並列化は試行単位のプロセス並列
- 乱数シード(`--seed`)は試行間で固定する(GA が評価雑音を最適化しないように)
- **1試行の所要時間を最初に実測し**、GA の世代数・個体数の見積もりに使う

### 7.2 転回率(Phase 3-②)

2通りを用意し、断面交通量比で比べる:

1. **転回率を直接調整**: `turns.xml` の確率を目的関数(断面交通量の誤差)で最適化する。
   design.md の方針どおり
2. **`routeSampler`**: センサス断面交通量(`edgeData` 形式に変換)を与え、
   `jtrrouter` が作った候補経路から観測に合う経路集合を選ぶ。
   OD を推定するのではなく**経路の重みを断面に合わせる**ので、design.md §3.1 の
   「粗い OD を細分化しない」方針には反しない

現状の交通量比 0.17(Phase 3-①)の主因が流入不足か転回かの切り分けは、
SUMO 版のベースラインが出た後に行う(自前実装側では行わない)。

### 7.3 オフセット(Phase 3-③)

§3.4 の追加ファイルを GA の個体ごとに生成する。ホールドアウト(センサス17区間の2割を外す)
の設計は変えない。

| 指標 | 自前実装 朝 / 昼 | SUMO 朝 / 昼 |

| 区間速度バイアス | +0.5 / −2.6 km/h | **−7.9 / −11.7 km/h** |
| 区域全体の平均速度 | 11.7 / 11.0 km/h | 5.1 / 5.2 km/h |
| 流入できなかった車両 | 1,673 / 1,080(流入待ち) | 4,120 / 3,490(記録終了時の挿入待ち) |
| テレポート(立ち往生の強制移動) | — | 247 / 197(渋滞 115・譲り待ち 107・車線違い 25) |

同じ需要・同じ信号でも、SUMO のほうが**区域全体が詰まる**(グリッドロック)。
テレポートは特定の1か所ではなく区域全体に散らばり、交差点内で止まった車両が交差方向を
塞ぐ連鎖になっている。切り分けの実験(朝ピーク、交通量比):

| 変種 | 交通量比 | 挿入待ち | テレポート |
|---|---|---|---|
| 基準 | 0.08 | 4,120 | 247 |
| 右折専用車線なし | 0.09 | 4,052 | 244 |
| 無信号交差点を「規制なし」(互いに譲らない = 自前実装の扱いに近い) | 0.12 | 3,058 | 647 |

- 右折専用車線は原因ではない
- 無信号交差点の譲り(自前実装は交錯を扱っていなかった)が一因。残りは交差点内の占有と
  待ち行列の延伸という、自前実装が簡略化していた相互作用(netsim の docstring
  「交差点内の交錯待ち車両が交差方向を塞ぐ相互作用なし」)による
- つまり自前実装の交通量比 0.17 は、交差点の相互作用を省いた分だけ流れやすかった値で、
  **需要(既定値 500/150 台/時の流入 54 本、計 8,100 台/時)と転回率の見直しが要る**
  という Phase 3-① の結論は SUMO でより強く出た
- 1試行(2,400 秒、経路生成込み)の所要時間は約 110 秒

### 13.4 ネットワーク(環状通の内側、全道路、PLATEAU の道路ポリゴン)

**対象区域:** 環状通の内側 + 環状通。ケースの `region_polygon()` を環状通の区域に替える
(`case.toml` で行政界・DID・環状通を切り替えられるようにする)。`core_polygon()`(都心コードン)は残す。

**道路:** 区域内は全車道(徒歩道・庭園路・石段を除く)。`case.toml` の `[network]` を
「区域内は全道路」に切り替える。

**PLATEAU 札幌市(2020)LOD1 道路ポリゴンの使い方:**

| 用途 | 方法 |
|---|---|
| **幅員 → 車線数** | KSJ の各リンクに沿って、道路ポリゴンの幅を一定間隔で測る(中央値)。LOD1 の道路ポリゴンは歩道を含む道路全体とみられるので、車道幅への換算に仮定を置く(D1 で、センサスの車道幅員がある区間と比べて係数を決める) |
| **交差点の範囲** | PLATEAU の道路モデルは車道交差部で区切って整備する仕様。交差点の面に入る KSJ のノードを1つの交差点にまとめる(上下分離道路の交差点が複数ノードに分かれる問題の根本対策)。**階層(KSJ の階層順・橋・トンネル)が違うノードはまとめない**(立体交差は面が重なるだけ) |
| **交差点の形** | 交差点の面を SUMO のノードの形(`shape`)として渡す。交差点の大きさが実際の道路の形になる |

**車線数の決め方(優先順):** センサス → PLATEAU の実測幅員から推定 → KSJ の幅員区分。
OSM の `lanes` は取り込まず、PLATEAU からの推定の**校正と答え合わせ**に使う(§13.16)。
**交差点の転回:** OSM の `turn:lanes`・転回制約はほとんど入っていない(§13.16)ので使わず、netconvert の推定のまま。

PLATEAU-RoadNetwork-Generator(国交省)は使わない。出力はメソレベル(最小幅員は出るが、車線数・一方通行・車線の接続は無い)で、LOD1 からは中心線レベルのネットワークになるため、KSJ + 規制の今の層[2]に対する利点が小さい。道路ポリゴンは直接使う。

**既存の処理はそのまま使う:** 位相構築・conflation・単方向化・SUMO 変換、C1・C2 で直した不具合の対策
(長さ 0 の Edge、右折専用車線のコード、合流部の優先青、車線数の四捨五入)。

### 13.5 需要: ゾーン・初期 OD・観測への補正

**① ゾーン**

- **125 m メッシュ**(6 次メッシュ)をゾーンにする。区域内で約 2,600
- **人口**: 国勢調査 2020 の 125 m メッシュ(手元: `e-stat-census-converter`、および結合済みの
  `e-stat/国勢調査タイル化検証用データ/.../2020_pop_census_mesh125.parquet`)
- **従業者数**: 経済センサス(活動調査 2021)は 500 m メッシュまで。500 m の従業者数を、
  **PLATEAU の建物**(LOD1、用途の属性)の非住宅の延床面積で 125 m に配分する
- **外部ゾーン**: 環状通を横切る道路の端ごとに置く。交通量は環状通を横切るセンサス区間
  (50)と感知器で縛る。環状通そのものの通過交通も外部ゾーン間の OD として表す
- ゾーン → Edge の対応は SUMO の TAZ(`<taz>`)。メッシュのポリゴンから `edgesInDistricts.py` で割り当てる

**② 初期 OD(重力モデル)**

```
T_ij(t) = k(t) · P_i^α · A_j^β · exp(-γ · c_ij)
```

- 朝ピーク: 発生 P = 夜間人口、集中 A = 従業者数(通勤・通学が主)。夕方は逆
- c_ij = ゾーン間の所要時間(自由流、ネットワークの最短経路)
- 時間帯の形 k(t) は、センサス・感知器の時間帯別交通量の合計の時間変動から取る
- α・β・γ は既定値で始め、補正の結果を見て調整する
- 重力モデルは SUMO に無いので Python で計算し、tazRelation XML(時間帯別)で書き出す

**③ 配分(動的利用者均衡)**

- `od2trips` で時間帯別の OD をトリップにし、`duaIterate.py` を**メソ**で回して所要時間を反映した経路選択にする
- 初期経路は `marouter`(マクロの均衡配分、速い)で作り、`duaIterate` の反復を減らすことも検討する

**④ 観測交通量への補正**

候補を2つ用意し、D4 で比べて決める:

1. **Cadyts**(`cadytsIterate.py`): `duaIterate` の反復の中で、経路選択と需要を観測交通量に合わせる
   SUMO の標準的な較正方法。Cadyts 本体(Java の jar)は SUMO に同梱されていないので別途用意する
2. **routeSampler + OD 制約**: `duaIterate` の経路を候補にし、初期 OD(`--od-files`)と観測交通量
   (edgeData)を同時に制約して台数を決める

補正で OD が初期値から大きく離れたゾーンは、初期 OD の前提(人口・従業者数・γ)を疑う材料にする。

### 13.6 観測: センサスと JARTIC 車両感知器

**センサス時間帯別交通量**(C3a で整備済み、§13.11): 方向別 Edge 12,342 本、調査単位 184
(環状通の内側 59、環状通を横切る区間 50)。2021 年秋の平日。

**JARTIC 断面交通量(typeB、札幌方面)**: 車両感知器の 5 分値。取得済みの 2026 年 6 月分
(1.09 GB、配布は最新 1 か月分だけ)。札幌周辺の地点は 1,455(2 次メッシュ 644142 = 都心を
含む範囲で 618)。地点は DRM リンク番号とリンク終端からの距離で示され、座標が無い。
位置は次の順で特定する:

1. **交差点制御情報(typeC)の定義との突き合わせ**: typeC は交差点ごとの流入・流出リンクを
   DRM 番号で持ち、交差点の座標も分かる(231 交差点)。感知器のリンクが
   - 交差点 X の流出かつ交差点 Y の流入 → X→Y の区間(位置と向きが確定。114 地点)
   - 交差点 X の流入だけ(433 地点)/ 流出だけ(454 地点)→ X に接する流入/流出路のどれか。
     向きは地点名称の方向(下記)と道路の方位で絞る
2. **地点名称の住所**: 「北　１西１９　東西」「南１６西１１　北南」「月寒中央通　４　南南」の
   ように条・丁目や町名が入る。条・丁目は国交省の**街区レベル位置参照情報**(無償)や
   都心の格子座標で位置に直す
3. **方向**: 名称末尾の 2 文字(「東西」「北南」など)の意味を、位置と向きが確定した地点
   (1. の 114 地点)と一方通行の道路で確かめてから使う

位置を特定した地点は、5 分値を時間帯別の平日平均にし、センサスと同じ形式
(方向別 Edge の時間帯別交通量)で観測に加える。センサス(2021 年秋)と感知器
(2026 年 6 月)は時期が違うので、両方がある地点で比べて補正するか、重みを分ける。

### 13.7 現況再現の照合: 時間帯別交通量の相関

現況再現は、**観測とシミュレーションの時間帯別交通量の相関**で確かめる
(交通量配分・シミュレーションの現況再現で標準的な確認)。

| 見方 | 内容 |
|---|---|
| 時間帯ごとの地点間の相関 | 各時刻について、全観測地点の(観測, シミュレーション)の散布図。**相関係数 r・決定係数 R²・回帰の傾き**(1 に近いほど偏りが無い)・RMSE%・GEH < 5 の割合 |
| 地点ごとの時間変動の相関 | 各地点について、時刻推移(センサスは 12 / 24 時間、感知器は 5 分〜1 時間)の相関。ピークの立ち上がり・時刻のずれを見る |
| 区間速度 | **保留**。通常の現況再現では旅行速度も確かめるが、時間帯別の旅行速度の観測が無いため、当面は交通量の相関だけで判断する。センサスの区間別の旅行速度(朝夕混雑時・昼間非混雑時の 2 区分、上下別)は手元にあり、使う場合は MAE・バイアスで比べる |

- **推定側とホールドアウト(観測の単位の 2 割)を分けて**出す。ホールドアウトで相関が
  落ちなければ、観測に過適合していない
- センサスと感知器は別々にも出す(時期と観測方法が違うため)
- 散布図はレポートに図として残す(数値だけにしない)
- **受け入れ条件(目標値)**: 朝ピーク時間で、観測点全体の相関係数 r ≥ 0.9・回帰の傾き
  0.9〜1.1・GEH < 5 が 60% 以上。ホールドアウトで r ≥ 0.85。値は D4 の結果を見て見直す

### 13.12 C3b 第1版の結果と教訓

`scripts/55_estimate_demand.py`(ブランチ `feat/37-c3b-demand-estimation` に保存): ランダムな
起終点(randomTrips、Edge の長さ × 車線数で重み付け、6 万トリップ)→ duarouter → routeSampler
でセンサス断面交通量に合わせ、市全域メソで照合。混雑を反映した経路の引き直しを 3 回。

| 回 | 交通量比(推定側 / ホールドアウト) | GEH < 5 | 挿入待ち | テレポート |
|---|---|---|---|---|
| 1 | 0.24 / 0.30 | 3.4% / 5.6% | 13.6 万台 | 2.2 万 |
| 3 | 0.23 / 0.25 | 1.4% / 6.9% | 13.6 万台 | 1.9 万 |

- 推定需要は 1 時間約 19 万台。観測のある道路の台キロは観測の 69% しか満たせず、
  トリップの距離の **44% が観測の無い道路**だった。起終点が道路網全体にでたらめに散らばり、
  観測の無い市道や流入地点に負荷が乗って、市全域がグリッドロックした
- 効果が小さかったもの: メソの交差点制御の有無、routeSampler の `--minimize-vehicles`、
  混雑を反映した経路の引き直し。車線数の推定の修正(切り捨て → 四捨五入)でテレポートは
  2.5 万 → 1.9 万に減った
- センサスの代表信号交差点の青時間比(平均 41.6%)は、代表交差点が区間で最も容量の厳しい
  交差点のため、全交差点に当てはめると容量を低く見積もる。代表交差点を特定できないので使わない
- **教訓**: 断面交通量だけでは経路の起終点が決まらない。発生・集中の構造(ゾーンと初期 OD)が
  要る(§13.5)。観測点も増やす必要がある(§13.6)

### 13.16 D1c の結果(OSM の車線・転回情報)

Overpass API から 1 回取得し(`data/interim/osm_lane_tags.json` にキャッシュ)、充足を数える。

| 情報 | 充足 |
|---|---|

  ±30% 以内は約 6 割(センサスは区間の代表値で、感知器が全車線を数えているとは限らない)

|---|---|---|
| 汎用 | 位相構築・立体判定・conflation・単方向化・車線(層[2])、SUMO 変換(§2〜§6)、キャリブレーション枠組み | `src/<パッケージ>/` |
| 地域パラメータ | 平面直角座標系、KSJ メッシュ番号、JARTIC の配布ファイル・情報源コード、センサスの都道府県コード、ビューワの初期位置 | `cases/<name>/case.toml`(ケースは環境変数 `JPSUMO_CASE` で選ぶ。既定 sapporo) |
| ケース固有処理(コード) | 対象区域ポリゴン(`region_polygon()`)、札幌の格子座標(`to_grid`・`GRID_BEARING_DEG`)・コードン定義 | `src/jp_sumo_traffic_sim/cases/<name>.py`(import できるようパッケージ内に置く) |
| ケース固有スクリプト | 札幌の格子推定・通し街路の命名・街路インベントリ(旧 scripts/02〜04) | `cases/<name>/scripts/` |
| シナリオ | 冬季(積雪地域向け。車両パラメータ・幅員縮小)、信号停止など | 汎用部のシナリオとして持ち、ケースで有効化する |

`config.py` の定数のうち地域に依存するものはケース設定から読むように変える。
閾値(端点スナップ 0.5 m、線規制のバッファ・方位角など)は札幌で実測して決めた値なので、
**既定値として汎用部に置き、ケースで上書きできる**ようにする。

### 14.2 地域ごとに再検証が要る前提

| 前提 | 札幌での確認 | 他地域 |
|---|---|---|
| JARTIC 規制のポリライン頂点順が通行方向の**逆** | OSM 照合 51 件中 50 件で確認(design.md §9) | **要再検証**。OSM 照合(scripts/15)をケースごとに必ず通す |
| JARTIC で提供される規制の種類 | 北海道は指定方向外進行禁止・停止線の提供なし | 都道府県で提供差がある(design.md §4.3) |
| 交差点制御情報の情報源コード | 北海道は5コード(札幌 3001 など) | 都道府県ごとに確認 |
| 平面直角座標系 | XI 系(EPSG:6679) | ケースごとに系を指定 |

### 14.3 進め方

- パッケージ名(旧 `sapporo_sim` → `jp_sumo_traffic_sim`)の変更と、札幌固有部の `cases/sapporo/` への切り出しは
  **SUMO 移行の Step 1 の前**に行う(コード量が少ないうちに import の変更を済ませる)
- 2つ目のケースを作るまでは、汎用部の境界を札幌のコードだけで決めることになる。
  境界の妥当性は2つ目のケースで検証する

## 付録: `sumo_ksj_sapporo.md`(検討メモ)との差分

検討メモは ksj-route-search-api の parquet(生の KSJ)から SUMO を作る前提だった。
本書は Phase 1 の出力を入力にするため、次の点が異なる。

- 座標系は **EPSG:6679(XI系)**。メモの EPSG:6680(XII系)は札幌では誤り
- `--shapefile.all-bidirectional` は使わない(一方通行 286 本は JARTIC で反映済み)
- `--tls.guess` は使わない(信号 173 ノードは JARTIC・層[2]で確定済み)
- `--junctions.join` / `--geometry.remove` は使わない(§2.3)
- 需要は `randomTrips` ではなくセンサス流入 + 転回率(§4)
