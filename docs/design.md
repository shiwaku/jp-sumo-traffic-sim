# 札幌都心部 ミクロ交通シミュレーション 基礎資料

作成日: 2026-08-21
用途: ローカル環境(Claude Code)で実装を進めるための設計・データ仕様

---

## 1. 目的とスコープ

### 1.1 やること

札幌市中心部を対象に、**車両1台ごとを再現するミクロ交通シミュレーション**を構築する。

主な関心事:

- 系統制御(信号オフセット)の効果検証
- 冬季の実質車線数減少が交通流に与える影響
- 街区長が短いことによるスピルバック(滞留長が上流交差点を塞ぐ現象)

### 1.2 対象区域

札幌都心の矩形区域。碁盤目かつ外周が幹線で囲まれているため、コードン(境界)の設定が容易。

| 方位 | 境界 |
|---|---|
| 北 | 北5条通 |
| 南 | 南7条通 |
| 東 | 創成川通 |
| 西 | 石山通(国道230号) |

- 概算 1.5km × 1.2km
- 交差点数 50〜70
- コードン流入点 30〜40箇所
- 街区間隔: 東西方向の通り間隔 約110m / 南北方向 約60m

**街区が短いことが本質的。** 赤信号の待ち行列が街区長を超えて上流交差点を塞ぐ挙動は、マクロ/メソモデルでは表現できずミクロでのみ再現される。この区域を選ぶ主要な動機。

### 1.3 やらないこと(初期段階)

- OD行列の推定 → コードン流入 + 転回率で代替(第3章参照)
- 歩行者の明示的モデル化 → 地下歩行空間により地上横断が少なく、影響が小さい
- 市電(併用軌道)の詳細再現 → 初期は除外または近似
- 市全域への拡張

## 2. モデル仕様

### 2.1 参照論文

Saval A, Minh DP, Chapuis K, Tranouez P, Caron C, Daudé É, Taillandier P (2023)
"Dealing with mixed and non-normative traffic. An agent-based simulation with the GAMA platform"
PLoS ONE 18(3): e0281658
https://doi.org/10.1371/journal.pone.0281658

- ライセンス CC BY 4.0
- モデル実装は GAMA 1.8.2 以降に driving skill として同梱
- 補足データ: https://doi.org/10.6084/m9.figshare.21369090.v1 (アクセス不安定。GAMA本体から取得可)

### 2.2 縦断挙動: IDM (Intelligent Driver Model)

Treiber, Hennecke, Helbing (2000) Phys Rev E 62:1805

```
dv/dt = a * [ 1 - (v/v0)^delta - (s*(v, dv) / s)^2 ]

s*(v, dv) = s0 + max(0, v*T + (v * dv) / (2 * sqrt(a*b)))
```

| 記号 | 意味 | 平常時 | 冬季 |
|---|---|---|---|
| `a` | 最大加速度 [m/s²] | 1.2 | 0.7 |
| `b` | 快適減速度 [m/s²] | 1.8 | 0.55 |
| `s0` | 最小車間 [m] | 2.5 | 5.0 |
| `T` | 車頭時間 [s] | 1.3 | 1.6 |
| `v0` | 自由走行速度 [m/s] | 規制速度 × 係数 | × 0.7 |
| `delta` | 加速指数 | 4 | 4 |

`v0` は道路の規制速度に運転者の遵法傾向係数 `coeff_v` を乗じて算出する。

### 2.3 横断挙動: MOBIL

Kesting, Treiber, Helbing (2007) Transportation Research Record 1999:86-94

安全基準:
```
a_new_follower >= -b_safe
```

インセンティブ基準:
```
(a_c_new - a_c_old) + p * (a_n_new - a_n_old) > a_th + a_bias
```

- `p`: 他者への配慮係数
- `a_th`: 車線変更の閾値
- `a_bias`: 非対称項。**日本は左側通行のため、論文(右側通行)と符号を反転させる**

### 2.4 信号の扱い

論文の実装に従う。

- **赤信号 = 長さ0の停止車両** として IDM に投入する
- 青に変われば通常の交差点に戻す
- 遵守確率 `p_respect_stops` で違反を確率的に表現(日本では 1.0 近傍を既定とする)

### 2.5 サブレーン

道路幅員を「最小車両1台分の幅」で分割し、車両は複数サブレーンを占有する。

- 二輪 = 1サブレーン
- 乗用車 = 2〜3サブレーン

**用途(札幌):**

1. 二輪のすり抜け
2. **冬季の幅員狭小** — 路肩の雪堆積を「サブレーン数の時間変化」として表現できる。整数の車線数では表せない「片側2車線が実質1.5車線」という中間状態を扱える
3. 右折専用車線 — 特定サブレーンのみ通行可として表現
4. 路上駐車 — 特定サブレーンを塞ぐ速度0の車両として配置

### 2.6 計算規模の見積もり

論文の実測(Mac mini M1 / 8GB):

- 計算時間は車両数に対してほぼ線形
- 10万台でも許容範囲

対象区域のピーク1時間の同時走行台数は数千台のオーダー。**性能はボトルネックにならない。**

## 3. 需要側(交通発生)の設計

### 3.1 なぜODを使わないか

公表されているOD表はミクロには粗すぎる。

- センサスOD調査: 政令市では行政区が1ゾーン規模。中央区(約46km²)が1点に潰れる
- 札幌都市圏PT調査: 数百ゾーン規模。街区単位には届かない

粗いODを細分化(disaggregation)する際に入る誤差のほうが、ODを使わない場合の誤差より大きくなりうる。

**経路選択を扱わないならODは不要。** ODが必要になるのは新設道路による交通転換の評価や、避難シミュレーションのように全員が同時に別目的地へ向かうケース。

### 3.2 採用方式: コードン + 転回率

```
区域境界の流入点(30〜40箇所) → 時間帯別の流入台数を与える
各交差点 → 方向別転回率(直進/左折/右折)で分岐
区域内の発生・集中 → 大規模駐車場を発生源として個別配置
```

**未知数の数:** 交差点数 × 流入方向 × 3。50交差点なら約600個だが、各交差点で合計1という制約があるため実質はその2/3。ODの2500ペアより桁違いに少ない。

**推定方法:** 上下流の断面交通量の差から転回率を絞り込む。主要交差点は現地観測で直接計測。

### 3.3 出発時刻分布

センサスの時間帯別交通量表をそのまま使う。ピーク形状はここから取れるため、逆推定の対象外。

### 3.4 区域内発生

大規模駐車場(地下街、大型商業施設、オフィスビル)の位置と容量を発生源とする。

調達候補: 札幌市の駐車場条例関連資料、大規模小売店舗立地法の届出情報。

| 属性 | 名称 | 用途 |
|---|---|---|
| N13_001 | データ登録日 | — |
| N13_002 | 種別 | — |
| N13_003 | 道路分類 | 1=国道 2=都道府県道 3=市区町村道等 4=高速自動車国道等 |
| N13_004 | 道路状態 | — |
| N13_005 | **階層順** | 立体交差の判別。誤接続防止に必須 |
| N13_006 | **幅員区分** | サブレーン数の算出元 |
| N13_007 | 有料区分 | — |
| N13_008 | 二次メッシュ番号 | — |

**精度の腑分け:**

仕様上の位置正確度は「水平位置の標準偏差 25m」。ただしこれは絶対位置精度であり、形状(相対精度)の忠実度とは別。

- **シミュレーション内部** → 相対形状が効く。地図全体の平行移動は結果に影響しない。**問題にならない**
- **他データとの空間結合** → 絶対精度が効く。バッファ半径の設計に影響。**実測で決めること**

## 5. データ処理パイプライン

### 5.1 全体構成

```
KSJ N13 (6441)          → 道路中心線・階層順・幅員区分
  ↓ 位相構築
道路ネットワーク(ノード・リンク)
  ↓ conflation
JARTIC 交通規制情報      → 一方通行・最高速度・一時停止・転回制約
JARTIC 交差点制御情報    → サイクル長・スプリット
センサス箇所別基本表     → 車線数・幅員・大型車混入率
航空写真からの手入力     → 停止線位置・右折レーン
  ↓
シミュレーション入力データ
  ↓
IDM + MOBIL + 信号
  ↓
道路ID別の指標(平均速度・密度・滞留長)
  ↓ link_id で join
PMTiles + setFeatureState で可視化
```

### 5.2 位相構築(最初の工程)

KSJは端点分割済みだが位相を持たないため、自前で構築する。

**判断すべき点:**

1. 端点一致の許容誤差(何mまで同一ノードとみなすか)
2. **階層順(N13_005)が異なる端点は接続しない** — これを入れないと高架から一般道に降りる車が発生する
3. 交差点内の極短リンク(数m)の扱い — 車長5mの車両が複数リンクにまたがるとIDMが破綻する。閾値以下のリンクは統合するか、交差点内部として別扱いにする

**先に確認すべきこと:**

- 端点の一致状況(許容誤差ごとの接続率)
- 階層順の分布
- リンク長の分布(特に短いリンクの数)
- 幹線(創成川通・石山通)が上下線で別リンクか、1本か

### 5.3 Conflation(規制情報の紐づけ)

**共通キーが存在しない**ため、すべて空間結合になる。

| データ | 識別子 |
|---|---|
| KSJ | 自前生成のリンクID |
| センサス | 交通調査基本区間番号 |
| JARTIC 交差点制御・断面交通量 | 交通管理技術協会リンク番号 |
| JARTIC 交通規制 | 座標のみ(+都道府県別ユニークキー) |

**規制形態ごとに手法が変わる。着手順序 = 面 → 点 → 線**

**(a) 面規制(ゾーン30等)** — ポリゴン内包判定。最も簡単。座標系と単位の健全性を安価に検証できるため最初に実施。

**(b) 点規制(一時停止・信号機)** — 最近傍ノードにスナップ(KDTree)。

ただし**一時停止は方向を持つ**。「この交差点のこの流入方向だけ」なのでノードに落とすと情報が落ちる。標識座標から最寄りノードを引き、そのノードに接続するリンクのうち標識座標に最も近い側を流入リンクとして特定する。

**(c) 線規制(一方通行・最高速度)** — 最も難しい。

- バッファ内判定 **+ 方位角差が閾値以内** の両方を条件にする。方位角条件がないと交差点付近で直交道路を誤マッチする
- **一方通行の向きが最重要。** ポリラインの頂点順が通行可能方向を示すはず(仕様書で要確認)。符号を逆にすると逆走するネットワークができ、結果は一見もっともらしいのに全部間違う

**バッファ半径は実測で決める。** 対応が明らかな規制点を数個選び、KSJリンクまでの実距離を測る。仕様上の25mを素直に使うと、街区110mの都心では隣の道路を拾う。

### 5.4 Conflation の検証

**OSMの一方通行タグを答え合わせに使う。**

```
JARTIC → KSJ 結合結果の oneway
  vs
OSM の oneway タグ(空間的に対応するway)
```

一致率を出し、不一致箇所のみ目視確認する。不一致は「OSMの誤り」か「結合の誤り」のどちらかであり、いずれにせよ確認価値がある。都心の一方通行は本数が限られるため全件確認も現実的。

結合率は `join_report.json` 相当のファイルに記録し、更新のたびに差分を追える形にする(jartic-traffic-signal-cycle-converter の設計を踏襲)。

### 5.5 手入力する項目

区域が小さいため、パイプラインを組むより手作業のほうが速く正確。

| 項目 | 出典 | 工数目安 |
|---|---|---|
| 停止線位置 | 国土地理院 正射画像 | 50-70交差点で1-2日 |
| 右折専用車線の有無・長さ | 同上 | 同上 |
| 車線数(細街路) | 同上 | 同上 |

**停止線と右折レーンはどのオープンデータにも存在しない。**

- 停止線: 位置が数m違うと滞留長が変わる。論文が交差点を「長さ0の車両」として扱う以上、位置精度が直接結果に効く
- 右折レーン: 無いと右折待ちが直進を塞ぎ、**渋滞が過大に出る**

### 5.6 座標系

| データ | CRS |
|---|---|
| KSJ N13 | JGD2011 地理座標 |
| センサス R03 | EPSG:4612 |
| JARTIC 規制 | 世界測地系(要確認) |

**シミュレーション用の投影: EPSG:6679 (JGD2011 / 平面直角座標系 XI系)** — 札幌は11系。距離・速度計算を素直にするため必須。

微妙なズレがあると数メートル単位の誤差になる。スナップ半径を決める前に、明らかに対応する点を数個手で確認しておく。

## 6. キャリブレーションと検証

### 6.1 推定するパラメータ

| パラメータ | 備考 |
|---|---|
| **信号オフセット** | JARTICに含まれない。最重要 |
| 転回率 | 断面差から絞り込み、残りを推定 |
| IDM の `T`, `s0` | 飽和交通流率を決める |
| MOBIL の `a_th`, `a_bias` | |
| 冬季の `v0`, `a`, `b` 低減率 | |

**オフセットは推定可能な未知数。** サイクル長とスプリットが既知なので、論文がGAでIDM/MOBILパラメータを推定したのと同じ枠組みに乗る。

理論上の最適オフセット = 交差点間隔 ÷ 自由速度。札幌都心の東西方向(110m間隔)で50km/hなら約8秒。ただし実際は街区が短く滞留の影響が大きいため、理論値からずれる可能性が高い。

### 6.2 目的関数

論文に倣い、観測時系列との差を最小化する。

- SSE(二乗誤差和)
- DTW(動的時間伸縮)

窓サイズ10秒。車種別に重み付け(`DTW_car × N_car + DTW_truck × N_truck`)。

### 6.3 検証指標

**(a) 断面交通量の時系列** — センサス時間帯別 / 断面交通量情報 / 交通量API(5分値)

**(b) 混雑時旅行速度** — センサスに実測値がある

**(c) 滞留長 ← この区域固有の強力な指標**

街区が110m/60mと短いため、赤信号での車列が街区長を超えるかどうかが目視・動画で判定しやすい。

> 例: 「南1条通の東行き、朝8時台に西4丁目交差点の車列が西5丁目まで届く」

断面交通量が合っていても滞留長が合わなければ、車頭時間や飽和交通流率の設定が誤っていると切り分けられる。**断面カウントだけでは検出できない誤りを捕まえられる。**

### 6.4 ホールドアウト検証

論文はTay Sonでキャリブレーションし、Chua Bocで検証した。同じ構造を踏襲する。

- 観測点の2割を推定から外す
- 推定パラメータでの再現値が、外した点でどれだけ合うかを見る
- ここが合わなければ「与えた観測に過適合しただけ」

### 6.5 冬季の重要な仮説

**同じ信号設定のまま冬になると系統がズレる。**

自由速度が下がるため最適オフセットが変わる。除雪や規制以前に、**信号パラメータ自体が季節依存**という論点。実務的にも検証価値がある。

## 8. 実装基盤の選択

### 8.1 GAMA を使う場合

- driving skill / road skill / intersection skill の3点セット
- GAML言語で記述。Javaを書かずに拡張可能
- 参考: https://github.com/gama-platform/gama Wiki の `UsingDrivingSkill`
- サンプルモデル: `simtools.gaml.extensions.traffic/models/Driving Skill/models/`
- 関連リポジトリ: https://github.com/ACROSS-Lab/TrafficLab

**利点:** IDM/MOBIL/サブレーン/非規範行動が実装済み。論文と同一の実装で比較可能。

**欠点:** GUIが重い。Web共有しにくい。データ入出力の自由度が低い。

### 8.2 自前実装する場合

Python(またはRust)でコアを書き、可視化はMapLibre + PMTiles。

**利点:** データパイプラインと統合しやすい。GAでのキャリブレーションを回しやすい。出力形式が自由。

**欠点:** IDM/MOBIL/サブレーンを自分で書く。検証工数が増える。

### 8.3 推奨

**Phase 2までは自前実装、必要ならGAMAで相互検証** が現実的。

理由: データ処理(conflation、パース、投影)がPythonエコシステムに依存しており、そこからGAMAへの受け渡しがボトルネックになる。またキャリブレーションで数百回シミュレーションを回すため、ヘッドレスで高速に動く実装が要る。

なお、既に動作する簡易版がある: `sapporo-grid-sim.html`(IDM + 定周期信号 + オフセット + 冬季モード)。オフセットの効き方を体感するプロトタイプとして機能する。
