# 実装設計書

`docs/design.md` は**何を作るか・どのデータを使うか**を定めた基礎資料。
本書は**どう作るか**を定める。データ構造・モジュール境界・アルゴリズム・
ファイル形式・テストの受け入れ条件を扱う。

Phase 0 の実測(`docs/phase0-findings.md`)を前提にしている。
設計資料と実測が食い違う箇所は実測に従う。

## 1. 全体構成

5つの層に分ける。層をまたぐ依存は下向きのみ。

```
[5] 可視化          reports/*.csv → PMTiles + setFeatureState
                          ↑ link_id で join
[4] キャリブレーション  GA / 目的関数(SSE・DTW)/ ホールドアウト検証
                          ↑ ヘッドレスで数百回シミュレーションを回す
[3] シミュレーション    Eclipse SUMO(IDM + サブレーン車線変更 + 信号 + 交差点)
                          ↑ 層[2]の出力を SUMO 入力へ変換する(sumo/)
[2] ネットワーク       位相構築 → conflation → 単方向エッジ化 → レーン展開
                          ↑ 空間結合はここで完結させる
[1] データ取得         KSJ / JARTIC / センサス / 手入力
```

**層の分離が守るべき性質:**

- 層[3]は SUMO。層[2]の出力から**機械的に再生成できる**入力(net.xml・経路・追加ファイル)
  だけで動かし、手で net.xml を編集しない(docs/sumo-design.md §0)
- 層[2]の出力は**不変**。シミュレーション中に変わるのは信号現示と車両の状態だけ
- 層[4]は SUMO を試行ごとに起動する。試行間で変わるのは追加ファイル(オフセット・
  vType・経路)だけで、net.xml は共有する(sumo-design.md §7.1)

## 2. 座標系とグリッド座標

| 用途 | 系 |
|---|---|
| 入力(KSJ N13) | EPSG:6668 JGD2011 地理座標 |
| 空間処理・シミュレーション | **EPSG:6679** JGD2011 平面直角座標系 XI系 |
| 街路の同定・コードン定義 | **グリッド座標 (u, v)** |

グリッド座標は EPSG:6679 を `GRID_ORIGIN` 中心に `-GRID_BEARING_DEG`(10.906度)
回転したもの。`u` が東西(丁目)、`v` が南北(条)。
札幌都心は 130.0m の等間隔格子なので、この系では

```python
S.v_south(1)   # 南1条通の v(S = jp_sumo_traffic_sim.cases.sapporo)
S.u_west(11)   # 西11丁目通(石山通)の u
```

で街路が名指しできる。**街路の同定は連鎖クラスタリングではなく格子への直接割り当てで行う**
(Phase 0 で連鎖が隣の通りまで結合する不具合を確認済み)。

変換は `cases.sapporo.to_grid()` / `from_grid()` のみを使い、
回転角と原点をスクリプト側に散らさない。散らすと街路の横断座標が
実行ごとにずれてインベントリが壊れる。

## 3. データモデル

### 3.1 層[2]の出力(不変)

`data/processed/network.gpkg` + `network.json`。

**Node** — 交差点および道路端点

| 列 | 型 | 説明 |
|---|---|---|
| node_id | str | `N#####` |
| x, y | float | EPSG:6679 |
| u, v | float | グリッド座標 |
| kind | enum | `junction` / `dead_end` / `cordon` / `internal` |
| street_u, street_v | str | 交差する街路名(例 `南1条通` × `西4丁目通`) |
| has_signal | bool | JARTIC 交差点制御情報と結合できたか |
| jartic_id | str? | `情報源コード-交差点番号` |

`street_u` × `street_v` の組が**人間が読める交差点名**になる。
検証で「南1条通の東行き、西4丁目交差点の車列」を指す際にこれを使う。

**Edge** — 単方向の道路区間。双方向道路は2本に分ける

| 列 | 型 | 説明 |
|---|---|---|
| edge_id | str | `E#####` |
| from_node, to_node | str | |
| ksj_link_id | str | 由来の KSJ リンク(トレーサビリティ) |
| street | str | 所属街路名 |
| length_m | float | |
| n_lanes | int | 車線数 |
| n_sublanes | int | サブレーン数(§5.3) |
| speed_limit_kmh | float | 規制速度。JARTIC 規制情報または既定値 |
| width_class | str | KSJ N13_006 |
| road_state | str | KSJ N13_004。`tunnel` / `bridge` は立体 |
| linked_edge | str? | 対向車道の edge_id |
| oneway_source | enum | `jartic` / `osm_checked` / `manual` / `assumed` |
| geometry | LineString | 進行方向に頂点を並べる |

**進行方向 = 頂点順** を不変条件にする。
一方通行の向きを間違えると逆走するネットワークができ、
結果は一見もっともらしいのに全部間違う。`oneway_source` を必ず残し、
`assumed` が残っている本数をレポートに出す。

**Movement** — 交差点での転回

| 列 | 型 | 説明 |
|---|---|---|
| movement_id | str | |
| node_id | str | |
| in_edge, out_edge | str | |
| turn | enum | `through` / `left` / `right` / `u_turn` |
| allowed | bool | 指定方向外進行禁止を反映 |
| signal_group | str? | どの現示で青になるか |
| turn_ratio | float | 転回率(キャリブレーション対象) |
| lanes | list[int] | この転回に使える車線 |

**StopLine** — 停止線。航空写真からの手入力

| 列 | 型 | 説明 |
|---|---|---|
| edge_id | str | |
| offset_m | float | to_node からの距離 |
| source | enum | `manual_ortho` / `assumed` |

停止線の位置が数m違うと滞留長が変わる。
論文が交差点を「長さ0の車両」として扱う以上、位置精度が直接結果に効く。
`assumed` の割合をレポートに出し、キャリブレーション前に潰す。

**SignalPlan** — 信号現示計画

| 列 | 型 | 説明 |
|---|---|---|
| node_id | str | |
| cycle_s | float | JARTIC サイクル長 |
| offset_s | float | **キャリブレーション対象** |
| phases | list | 各現示の green_s / yellow_s / allred_s と signal_group |

JARTIC のスプリットは青+黄+全赤の合計。
標準値(黄3〜4秒 / 全赤2秒)を差し引いて青時間を出す。
差し引き規則は1箇所(`network/signals.py`)に閉じ込め、現地観測で校正する。

### 3.2 層[3]の状態(可変)

車両・信号の状態は SUMO が持つ。本リポジトリ側では持たない。
層[3]の入出力は docs/sumo-design.md §1 の図のとおり
(`data/sumo/` の net.xml・経路・追加ファイル → edgeData・statistic-output・FCD)。

> 自前実装では車両を Structure of Arrays で持ち、エッジ単位の連結リストで先行車を
> O(1) で引く設計だった(Phase 2、撤去済み)。

## 4. 層[2] ネットワーク構築

### 4.1 位相構築(`network/topology.py`)

```
KSJ リンク
  → 端点抽出
  → 0.5m でクラスタリング(union-find + KDTree)
  → 立体判定で接続を間引く
  → 短リンク統合
  → Node / 無向 Link
```

**端点スナップ:** 許容誤差 `SNAP_TOL_M = 0.5m`。
Phase 0 で 0.01〜1.0m は結果が不変、2m 超で誤結合が始まることを確認済み。

**立体判定:** `(N13_005 階層順, N13_004 道路状態)` の組で行う。

```python
def is_grade_separated(link) -> bool:
    return link.road_state in ("2", "3")  # 橋・高架 / トンネル
```

**階層順だけでは不十分。** 創成トンネル(887.2m × 2本)は階層順0のまま入っている。
立体リンクは端点(坑口・橋端)以外で地表と接続させない。
KSJ は交差点でのみ分割するため、立体リンクは端点を2つしか持たない。
結果として確認すべきは坑口・橋端の4箇所だけになる。

**短リンク統合:** 長さ `SHORT_LINK_M = 12m` 未満のリンクは交差点内部として扱う。
Phase 0 の実測で 60本(5.8%)。
統合は次数2のノードを消す形で行い、次数3以上のノードに挟まれた短リンクは
**交差点を1つのノードに縮約**する。

> 30〜70m のリンクは統合してはいけない。
> 大通以南は裏通りがあるため実質街区長が65mであり、これらは正当な街区。

**受け入れ条件:**

- 到達可能性: 任意のコードン流入点から任意のコードン流出点へ経路が存在する
- 次数1ノードのうち、コードン境界上にないもの(真の行き止まり)を列挙してレポートに出す
- 立体リンクの端点以外に地表との共有ノードが無い

### 4.2 Conflation(`network/conflation.py`)

**共通キーが存在しない**ため、すべて空間結合になる。
着手順序は **面 → 点 → 線**。座標系と単位の健全性を安価に検証できる順。

| 段 | 対象 | 手法 |
|---|---|---|
| 面 | ゾーン30 等 | ポリゴン内包判定 |
| 点 | 一時停止・信号機 | 最近傍ノードへスナップ(KDTree)+ **流入リンクの特定** |
| 線 | 一方通行・最高速度 | バッファ内判定 **かつ** 方位角差が閾値以内 |

**点規制の方向:** 一時停止は「この交差点のこの流入方向だけ」。
ノードに落とすと情報が落ちる。標識座標から最寄りノードを引き、
そのノードに接続するリンクのうち標識座標に最も近い側を流入リンクとして特定する。

**線規制の方位角条件は必須。** バッファのみだと交差点付近で直交道路を誤マッチする。
札幌都心は格子が130mなので、仕様上の位置正確度25mを素直にバッファ半径にすると隣の道路を拾う。
**バッファ半径は実測で決める:** 対応が明らかな規制点を数個選び、
KSJ リンクまでの実距離を測ってから決定する。

**一方通行の向き:** ポリラインの頂点順が通行可能方向を示すか、仕様書で確認する(未解決)。
符号を逆にすると逆走するネットワークができる。
OSM の oneway タグで一致率を出し、不一致箇所のみ目視する。
都心の一方通行は本数が限られるため全件確認も現実的。

**`reports/join_report.json`** に段ごとの結合率を記録する。
更新のたびに差分を追える形にする(jartic-traffic-signal-cycle-converter の設計を踏襲)。

```json
{
  "stage": "line_oneway",
  "n_source": 0, "n_matched": 0, "match_rate": 0.0,
  "buffer_m": 0.0, "bearing_tol_deg": 0.0,
  "osm_cross_check": {"n_compared": 0, "n_agree": 0, "agree_rate": 0.0}
}
```

### 4.3 単方向エッジ化とレーン(`directed.py` / `lanes.py`)

無向 Link → Edge:

- 双方向道路は2本の Edge にし、互いを `linked_edge` で指す
- 一方通行は1本のみ
- `oneway_source` が `assumed` のものを数え上げてレポートに出す

**車線数の決定順:**

1. センサス箇所別基本表の車線数(幹線のみ、最優先)
2. 航空写真からの手入力(細街路)
3. KSJ 幅員区分からの推定(最後の手段)

**サブレーン:** 道路幅員を「最小車両1台分の幅」で分割する。

```
sublane_width = 1.75m   # 二輪1台分
n_sublanes = floor(carriageway_width / sublane_width)
```

- 二輪 = 1サブレーン、乗用車 = 2サブレーン、大型 = 3サブレーン
- **冬季は `n_sublanes` を時間変化させる。** 整数の車線数では表せない
  「片側2車線が実質1.5車線」を表現できる
- 右折専用車線 = 特定サブレーンのみ通行可
- 路上駐車 = 特定サブレーンを塞ぐ速度0の車両

KSJ 幅員区分の代表値は `ksj_codes.WIDTH_REPRESENTATIVE_M`。
コードの並びは狭い→広いで、1 が最も狭い。**逆に読むと幹線と細街路が入れ替わる。**

## 5. 層[3] シミュレーション

**Eclipse SUMO** を使う(Phase 2 の自前実装から移行、issue #30)。
変換と実行の詳細は [sumo-design.md](sumo-design.md)。ここでは要点と、自前実装で得た知見を残す。

### 5.1 時間積分

`--step-length 0.5`(`sumo/runner.py`)。SUMO の IDM は内部でさらに細かく刻む。

> 自前実装で確認済み: 飽和交通流率は dt 0.5s → 0.2s で 1% も変わらない。効くのは IDM の `T` と `s0`。

### 5.2 IDM(`sumo/vtypes.py`)

```
dv/dt = a * [ 1 - (v/v0)^delta - (s*(v, dv) / s)^2 ]
s*(v, dv) = s0 + max(0, v*T + (v * dv) / (2 * sqrt(a*b)))
```

| 記号 | SUMO 属性 | 平常時 | 冬季 |
|---|---|---|---|
| `a` | `accel` | 1.5 | 0.7 |
| `b` | `decel` | 1.8 | 0.55 |
| `s0` | `minGap` | 2.0 | 5.0 |
| `T` | `tau` | 1.1 | 1.6 |
| `v0` | 規制速度 × `speedFactor` | `normc(0.95,0.08,0.7,1.3)` | × 0.7 |
| `delta` | `delta` | 4 | 4 |

> 平常時の値は飽和交通流率 1800〜2000 台/時/車線の再現から決めた(Phase 2-①)。
> SUMO での実測は 1,811 台/時/車線(`test_saturation_flow`)。
> 当初の a=1.2, T=1.3, s0=2.5 は約 1580 台/時にしかならない。冬季は Phase 3 でキャリブレーションする。

### 5.3 横断挙動(サブレーン)

`--lateral-resolution 1.75`(サブレーン幅 = `network.lanes.SUBLANE_W_M`)で SUMO の
サブレーン車線変更モデル SL2015 を使う。乗用車(幅 1.8 m)は約2サブレーンを占める。

**左側通行は netconvert の `--lefthand` で固定する。** 誤ると右折が対向と交錯せず、
追越が逆になる。`test_lefthand_overtake_on_right`(遅い車を右から追い越し、左へ戻る)で固定。

> 自前実装の MOBIL で得た知見: 論文(右側通行)の `a_bias` の符号は左側通行で逆になる。
> インセンティブは自車幅ぶん先の整列まで見ないと、幅2の車に追越動機が出ない。
> 左右は純利得で比較する(逐次判定だとコスト0の左戻りが常に勝つ)。

### 5.4 信号と交差点(`sumo/tls.py`)

- 2現示(A 青 → 黄 3s → 全赤 2s → B 青 → 黄 → 全赤)。青は等分、右折は従属青 `g`
  (SUMO の交差点モデルが対向直進に譲らせる)
- サイクル長は JARTIC 計画(時間帯別の中央値)、無ければ 120 s
- 軸(A/B)とオフセットはケースのフック(札幌: グリッドの東西/南北、東行き green wave)
- `offset` = A 青の開始時刻(`test_signal_offset_is_start_of_a_green`)
- 出側に空きが無ければ交差点に進入しない / 交差点内で止まれば交差方向を塞ぐ、は
  SUMO の交差点モデルが扱う(スピルバックの伝播)
- 一時停止は `priority_stop`(流入 Edge を従道路にする)

### 5.5 需要(`sumo/demand.py`)

OD行列は使わない(都心区域)。コードン流入 + 転回率。

```
コードン流入点(無向次数1ノードから出る Edge)
  → 時間帯別の流入台数(センサス時間帯別交通量、無ければ分類の既定値)
  → 各 Edge で転回率(直進/左折/右折 = 0.70/0.15/0.15 を再正規化)に従って分岐
  → コードンから流出
```

- 経路は `jtrrouter` が出発時に作る(転回が各交差点で独立な確率なら、交差点ごとの抽選と統計的に同じ)
- 巡回の上限: 通過交差点数 30 を超えたら最寄りの流出点へつなぎ替える(後処理)
- 上下分離・並走車道では同じ転回クラスに複数の候補が入る。**最良1本だけにすると残りの
  Edge がどの流入からも選ばれず、ネットワークの半分が飢餓する**(Phase 3-① で発覚)。
  角度適合の重み `1/(1+ずれ)²` で全候補に配る
- 市全域では OD + 経路選択に切り替える(sumo-design.md §13)

**未知数:** movement 数 × 3。格子交点156なら約1400だが、
各交差点で合計1という制約があるため実質はその2/3。
OD の2500ペアより桁違いに少ない。

### 5.6 指標(`sumo/sim.py`)

| 指標 | SUMO の出力 | 用途 |
|---|---|---|
| 断面交通量 | `edgeData` の `left`(下流端の区間) | センサス断面交通量との照合 |
| 区間速度 | `edgeData` の `speed`(sampledSeconds 加重) | 混雑時旅行速度との照合 |
| **滞留長** | `--queue-output` | **この区域固有の検証指標**(未実装) |
| 挿入待ち・テレポート | `statistic-output` | 詰まりの診断 |

滞留長が街区長(65m/130m)を超えるかどうかは目視・動画で判定できる。
断面交通量が合っていても滞留長が合わなければ、車頭時間や飽和交通流率の設定が
誤っていると切り分けられる。

### 5.7 経緯: 自前実装(Phase 2、撤去済み)

Phase 2 では IDM・MOBIL・サブレーン・右折専用車線・冬季減幅を Python で自前実装した
(理想化グリッド `sim/simple.py` と実ネットワーク `sim/netsim.py` の2系統)。
SUMO へ移行した理由と、同じ条件での比較は sumo-design.md §0・§11.1。
自前実装は交差点での相互作用(無信号交差点の譲り、交差点内で止まった車両が交差方向を
塞ぐ)を省いていたため、同じ需要でも SUMO より流れやすかった(交通量比 0.17 vs 0.08)。

## 6. 層[4] キャリブレーション

### 6.1 推定するパラメータ

| パラメータ | 次元 | 備考 |
|---|---|---|
| 信号オフセット | 信号交差点数 | **JARTICに含まれない。最重要** |
| 転回率 | movement 数 × 2/3 | 断面差から絞り込み、残りを推定 |
| IDM の `T`, `s0` | 2 | 飽和交通流率を決める |
| 車線変更(SL2015)の `lcStrategic` / `lcKeepRight` など | 2〜3 | 自前実装の MOBIL `a_th` / `a_bias` に相当 |
| 冬季の `v0`, `a`, `b` 低減率 | 3 | |

**オフセットは推定可能な未知数。** サイクル長とスプリットが既知なので、
論文がGAでIDM/MOBILパラメータを推定したのと同じ枠組みに乗る。

理論上の最適オフセット = 交差点間隔 ÷ 自由速度。
実測の格子間隔130mで50km/hなら約9.4秒。
ただし大通以南は裏通りにより実質65m(約4.7秒)であり、
**南北で最適オフセットが異なる。** 単一の系統設定では両立しない可能性がある。

### 6.2 目的関数(`calib/objective.py`)

観測時系列との差を最小化する。

- SSE(二乗誤差和)
- DTW(動的時間伸縮)、窓サイズ10秒

車種別に重み付け: `DTW_car × N_car + DTW_truck × N_truck`。

### 6.3 実行形態

- 1試行 = SUMO を1回起動する。試行間で変わるのは追加ファイル(オフセット・vType・経路)だけで、
  net.xml は共有して再生成しない
- 1試行(都心区域、2,400 秒、経路生成込み)は約 110 秒
- 乱数シードを試行間で固定する。固定しないとGAが評価雑音を最適化する
- 並列化は試行単位(GAの個体単位)のプロセス並列。libsumo(プロセス内)も候補

### 6.4 ホールドアウト検証(`calib/holdout.py`)

論文は Tay Son でキャリブレーションし Chua Boc で検証した。同じ構造を踏襲する。

- 観測点の2割を推定から外す
- 推定パラメータでの再現値が、外した点でどれだけ合うかを見る
- ここが合わなければ「与えた観測に過適合しただけ」

## 7. 層[5] 出力と可視化

```
シミュレーション
  → reports/metrics_{scenario}.csv   (edge_id, t, speed, density, flow, queue_len)
  → PMTiles(エッジ形状。edge_id を feature id にする)
  → setFeatureState で時系列アニメーション
```

`ksj-route-search-api` の可視化アーキテクチャを踏襲する。
形状はタイルに焼き、指標は別途 CSV/JSON で配り、
ブラウザ側で `setFeatureState` で結合する。
指標が変わってもタイルを焼き直さなくて済む。

`edge_id` は `ksj_link_id` を保持しているため、KSJ に遡れる。

## 8. テスト戦略

論文の検証手順を踏襲する。**ここが再現できなければ設定か変換にバグがある。**
SUMO のテストは本番と同じ変換(`sumo.build`)で小さな検証ネットワークを作って回す。

| テスト | 内容 | 受け入れ条件 |
|---|---|---|
| `test_lefthand_overtake_on_right` | 2車線単路、遅い先行車 | **遅い車を右から追い越し**、抜いたら左へ戻る |
| `test_saturation_flow` | 単一信号交差点、待ち行列 45 台 | 飽和交通流率が 1800〜2000 台/時/車線 |
| `test_right_turn_yields_to_oncoming` | 対向直進ありの信号交差点 | 右折が従属青で譲る。対向ありで捌け量が半分未満、衝突 0 |
| `test_signal_offset_is_start_of_a_green` | 単一信号交差点 | offset = A 青の開始時刻 |
| `test_cross_net_lefthand_rt_lane_and_program` | 変換 | 右折専用車線は中央側で右折のみ、U ターンなし、2現示 |
| `test_real_net_grade_separation` | 実ネットワーク | 立体リンクが途中で地表と接続しない |
| `test_real_net_reachability_and_ids` | 実ネットワーク | Edge id の1対1対応、全流入から流出へ到達可能 |
| `test_turn_probabilities_renormalize_turn_classes` | 需要 | 転回クラスの再正規化、U ターン除外 |
| `test_topology_reachability` | 構築後のネットワーク | 全コードン流入点から全流出点へ到達可能 |
| `test_oneway_direction` | エッジの頂点順 | OSM との一致率が閾値以上 |
| `test_spillback`(未実装) | 65m街区 + 上流交差点 | 滞留長が街区長を超えたら上流が塞がる |

`test_spillback` は区域選定の理由そのものを検証する中核テスト。SUMO の滞留長出力
(`--queue-output`)を使って追加する。

## 9. ファイル・命名規約

```
data/raw/         取得したまま。改変しない。manifest.json に SHA256
data/interim/     中間生成物。いつでも捨てられる
data/processed/   層[2]の出力。シミュレーションの入力
reports/          診断レポート(JSON/CSV)。コミットする
```

- スクリプトは `NN_動詞_目的語.py`。番号順に実行すれば再現できる
- 各スクリプトは `reports/NN_*.json` を必ず出す。
  **数値をターミナルにしか出さないスクリプトは書かない**(差分が追えない)
- ID 接頭辞: KSJ リンク `K`、ノード `N`、エッジ `E`、movement `M`
- 閾値は必ず `config.py`(地域依存なら `cases/<name>/case.toml`)かモジュール冒頭の定数にする。式の中に埋めない
